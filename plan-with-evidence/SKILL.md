# 需求解剖与证据规划

把用户愿望转为可以执行和验收的路线。统一判断方法，保留各领域的专业标准。先判断用户要分析、规划还是实施；规划请求不自动授权开发或外部操作，已有实施授权也不因使用本 Skill 而重新索要。

本 Skill 提供规划判断，不替代领域执行规范。进入网站、视频等具体制作时，按任务需要使用环境中可用的专业 Skill 或资料；能力缺失时说明限制，不假设工具存在。

## 按任务选择深度

- 输入输出明确、低成本且可逆：直接执行，必要时说明假设，不制造访谈和完整规划文档。
- 范围清楚但存在关键未知：只澄清会改变路线的部分，先做最小可行实验。
- 多阶段、返工昂贵或依赖尚不明确：形成需求契约、能力链、风险顺序和阶段门禁。
- 目标已清楚但实际结果异常：进入故障诊断；若诊断推翻目标可行性或成本假设，再回到本流程。无需为交接强制安装另一个 Skill。

## 主动质询关键缺口

先读现有材料、代码、样本和对话中的已确认决定。不要让用户回答能自行查明的事实。

对缺失信息做一次判断：不同答案会不会改变目标、完成标准、主路线、重要成本或权限？会且无法从现有证据确认时主动追问；否则说明合理假设并推进。

每轮优先问最关键的 1–3 个问题，每个说明影响，能推荐时给出理由。问题形式举例：“这里的‘全部’包括已删除内容吗？这会改变可实现范围和验收方式。”避免预设技术答案。

阻塞性答案未到时，仅推进不依赖该答案的工作。用户已给过预算、范围或授权，不重复索取；新事实实质改变选择时解释变化再问。质询用于帮助决策，不用于无限延迟开工。

## 工作流程

1. **定义结果。** 明确使用者、场景、最少输入、可交付输出、范围、非目标和完成证据。把“全自动、全部、高质量、便宜”等词变成可观察条件。审美、叙事效果等交付注明由谁、按什么参考评价。
2. **倒推必要能力。** 从最终结果反推前置产物和依赖，不先按工具或文件分模块。每个关键阶段写清输入、输出、失败状态和进入下一阶段所需证据。只拆到可以估计、验证和替换的粒度。
3. **辨认事实和假设。** 对影响主线的主张标明证据来源及尚未确定之处。能力“看起来可用”不能当成实际接口、可持续成本或完整覆盖已经成立。
4. **找关键路径和最大未知。** 同时考虑依赖顺序与验证顺序。按不确定性、失败影响、晚发现的返工成本进行相对排序，避免编造精确分数。优先验证足以否定整条路线的假设。
5. **设计最便宜的有效实验。** 写出要回答的问题、代表性样本、结果判据及停止条件。实验必须影响后续决策；昂贵调用先估算整体成本。创意任务用分镜、草图、样片获取反馈，不强行要求唯一正确答案。
6. **形成实施批次。** 推荐一条主线；只有具体依赖值得替换时给备选，并写切换条件。每批包含交付、依赖、验收证据。按风险验证连续运行、中断恢复或规模边界，不用首个样本代替整条链路验收。
7. **随证据调整。** 新证据改变路线时说明：原假设、反证、影响范围、保留资产、新决策及下一验证。不要因一个局部错误重写整个系统，也不要因已投入很多而继续失效路线。

## 输出与完成

按规模输出简明方案，通常包含：目标与边界、关键待确认项、能力与依赖、首要实验、分批交付和完成标准。不要为了格式填满无关栏目。

只有证据支持的部分才能称为已验证；推荐方案与已完成结果分开。数量有争议时先校准集合、单位、时间和处理阶段；创意交付区分技术合格与用户认可。

## 按需参考与成长

- 遇到范围口径、样本选择、工具能力混淆或方案取舍，读取 [条件模式](references/patterns.md) 的相关部分；模式是待现场验证的启发，不是每次必做的清单。
- 出现关键卡点、假设被推翻或路线转折时，在已有项目决策记录中保留最小证据。没有文档工作区时在交付中保留短记录，不保存凭据、无关数据或整段对话。
- 做项目复盘或用户要求改进本 Skill 时，读取 [成长规则](references/evolution.md)。普通项目只生成候选经验；只有明确授权更新 Skill 时才修改其持久内容。无需为“本次没有新增规则”请求确认。
- 创建或实质修改核心规则后，使用 [评估案例](references/evaluation.md) 比较可观察决策。结构合法、作者推演和独立行为验证分别报告。
